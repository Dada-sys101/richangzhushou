## Frozen user flow

```text
User Input
-> Fake Provider
-> Proposal
-> Proposal Review
-> uncertain / missing-field indication
-> user edit / supplement
-> user decision

Reject path:
-> Reject Proposal / Operation
-> REJECTED
-> terminal for rejected scope
-> NO Final User Confirmation
-> NO Domain Service write
-> NO formal business record

Accept path:
-> Accept intended Operation(s)
-> separate Final User Confirmation
-> existing formal Domain Service
-> formal business record
```

Accepting a Proposal is not the same action as finally confirming a business
write. These two gates must remain separate in the API, service orchestration and
UI.

## Mandatory safety invariants

1. AI must never automatically final-confirm.
2. Provider output must never write formal business tables directly.
3. Provider output must never call formal business write APIs directly.
4. One hundred percent of formal business writes require final user confirmation.
5. AI failure must preserve the user's original input.
6. Formal writes must go through the existing formal Domain Service.
7. User A must never read, edit, accept, reject, confirm or apply user B's
   Proposal or Operation.
8. Repeated final confirmation must not create duplicate business records.
9. Browser Back or reload must not submit an unconfirmed Proposal.
10. PR18 must not perform any real Provider call.

## Acceptance scope

### Proposal lifecycle

- Proposal and Operation are visible.
- Uncertain or missing fields have explicit indications.
- The user can edit/supplement, accept or reject.
- Final confirmation exists as a separate action from accept.

### No write before final confirmation

Negative tests must prove that the formal business-record count does not increase
before final confirmation. Proposal creation/view, field edits and Operation
acceptance must not create or modify a formal business record.

Rejected Proposal/Operation scope is terminal: it cannot be final-confirmed or
applied, must not invoke a formal Domain Service write and must not create or
modify a formal business record. An unaccepted or pending Operation cannot be
applied by final confirmation and must have no formal business side effect.

Mandatory negative coverage:

1. Reject, then attempt final confirmation: return a rejected/invalid-state
   result.
2. Reject: the formal business-record count remains unchanged.
3. Attempt final confirmation for an unaccepted Operation: the Operation is not
   applied and no formal side effect occurs.
4. For mixed Operations, only accepted scope may proceed to final confirmation;
   rejected or unaccepted scope is never written.

### Formal write after confirmation

After final confirmation, formal business data may be created or modified only
through the existing formal Domain Service. AI persistence and the Fake Provider
must not write domain tables directly.

### Idempotency and repeated confirmation

Repeated final confirmation, double-clicks, retries and duplicate requests must
produce at most one formal business side effect and no duplicate record.

### User isolation

User A must not read, edit, accept, reject, confirm or apply user B's Proposal or
Operation. Positive and negative isolation tests are mandatory.

### Failure recovery

Coverage must include Fake Provider controlled failure, confirmation-request
network failure, refresh/reload, Browser Back, restoration of original user input
and restoration of an incomplete Proposal.
